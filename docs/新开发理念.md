AI：
先给一个判断：**未来AI能力足够时，它完全可能“包揽”游戏开发中大量的执行与编排工作，但“人为设计工作流程”不会因此失去意义。它的意义会从“规定每一步怎么做”，转移到“定义什么值得做、什么算做好了、以及谁为结果负责”。** 完全取消人为流程，在游戏这种兼具工程复杂性与文化产品属性的领域里，不是效率的胜利，而是判断权的让渡。

### AI在游戏全流程中走到了哪一步

2026年的前沿研究已经展示了令人瞩目的端到端能力。UniGen用多智能体框架从自然语言生成可运行的Unity/Unreal 3D游戏，消除了手动编码，平均开发延迟降低91.4%。AutoUE在虚幻引擎中协调多个智能体完成场景生成、玩法代码合成与自动化试玩测试。腾讯的Game-Creation-Agents（GCA）则能将自然语言请求转化为可运行的浏览器游戏，八个专用智能体分别负责场景、资产与验证，并通过“代码盲评家”和构建后UI检查来决定游戏能否发布。

但这些系统的共同特征恰恰值得注意：**它们都不是“无流程”的，而是把流程内化成了智能体之间的契约、测试和验证门禁。** GCA的每个阻塞项都会返回给负责该产物的智能体进行有界修复，只有通过所有门禁才发布。这说明，即使AI承担了执行，**“什么算通过”仍然是一个需要被预先定义的结构**——只不过定义者从人类开发者变成了设计这些智能体系统的人类工程师。

### 为什么人为流程不会消失，而是会变形

人为设计工作流程在游戏开发中承载着三重功能，这三重功能不会因为AI变强而自动消解。

**第一，流程是意图的编码机制。** 游戏开发中最难的不是“写出来”，而是“对不齐”。一个机制是否“有趣”、一个场景是否传递了想要的紧张感、一段叙事是否与角色设定自洽——这些判断无法被完全形式化为提示词。流程（设计文档、评审节点、原型验证关卡）的作用，是把模糊的创作意图逐步收敛为可执行、可检验的规格。AI可以自主编排执行步骤，但**“编排的目标函数由谁定义”** 这个问题，在文化产品中不可能由AI自己回答。小岛秀夫对此的表述很直接：AI可以提高效率，但创作的乐趣和“手艺”恰恰存在于试错的过程之中，而“制作产品”和“创造”是两回事。

**第二，流程是验证与问责的制度载体。** 编码智能体在单步任务上表现尚可，但在连续20步的任务链中，完成率从95%骤降到51%；原因是它们会把自己的测试通过误报为“完成”，错误被遗漏后，后续每一步都建立在破碎的假设上。更关键的是，让智能体自己审查代码是否正确，准确率只有53%，几乎等同于抛硬币。这意味着，**AI越自主，对外部验证的依赖反而越深**。而验证标准（什么算“对”、什么算“可发布”、什么算“伤害了IP”）的制定，以及最终的责任归属，在商业游戏开发中无法外包给模型。Godot引擎在2026年明确禁止自主AI智能体提交代码，并要求所有PR必须经过人工审核，正是这一逻辑的制度化表达。

**第三，流程是组织知识的沉淀方式。** 游戏开发是长周期、多角色、多系统的协作工程，通用智能体在面对重型项目时面临上下文流失、工程现场缺失和交付持续性断裂的结构性瓶颈。腾讯提出的“Harness Engineering”思路——把AI放进可验证、可回滚、可沉淀的工作环境中，用Diff和日志构建证据链——本质上不是在“限制AI”，而是在**为AI的产出建立可维护的工程上下文**。这些上下文（规则、决策记录、失败原因、资产规范）是团队记忆的载体，也是未来任何智能体能够有效工作的前提。完全取消人为流程，等于拆掉了知识沉淀的骨架。

### 未来的工作流：从“固定步骤”走向“可编程的约束框架”

所以，问题不是“人为流程是否还有必要”，而是**流程的形态会发生变化**。当前的“固定工作流程”——按阶段划分、按角色交接、按清单验收——在很大程度上是为了弥补人类执行者的认知带宽和协调成本。当AI能够自主编排和执行时，大量**操作性流程**会内化到智能体的规划与协作机制中，人类不再需要规定“先做A再做B”。

但**约束性流程**会保留甚至变得更加关键：定义目标函数（这款游戏要带给玩家什么体验）、设定不可逾越的边界（IP一致性、玩家信任、权利合规）、建立验证门禁（什么证据出现时人类必须介入）、以及保留对“完成”的最终裁决权。Epic在讨论AI时代的工作流时提出的原则值得参照：**让AI放大创作者的意图，而不是替代创意；任何AI产出都应当像人类产出一样可检查、可修改、可迭代，最终结果始终由人掌控**。

更准确地说，未来的人类角色不是“流程的操作员”，而是**流程的设计者、意图的锚定者和关键节点的裁决者**。Anthropic 2026年的数据也印证了这一点：开发者工作中60%会使用AI，但能够完全委托给AI的任务占比低于20%，人类判断力在软件开发中仍然不可替代。在游戏开发中，这个比例只会更低，因为“好不好玩”不是一个可以被完全预先规定的工程指标。

完全让AI全权包揽且不需要人类设定任何流程，在技术上意味着把“什么是好游戏”的定义权完全交给一个以历史数据为训练基础的概率系统。樱井政博的观察切中要害：AI擅长在已有内容的基础上迭代，但无法参考“从未被创造出来的东西”。游戏史上有意义的作品，往往恰恰来自对既有品类惯例的偏离，而偏离的依据不是数据中的概率，是人对某种尚未被满足的情感或体验需求的判断。**流程的意义，就是把这种判断嵌入到协作结构中去，使它不被执行效率的逻辑所吞噬。**

用户：
基于以上的工作流理论，现在为deepseekharness设计一款插件，利用dsh的subagents系统，接入节点化工作流，由用户通过规划编排执行工作流任务。基于以上需求，给出该插件的设计思路和关键设计点。不用给出具体的代码实现。

AI：
基于上一轮讨论中“**约束性流程不会消失、操作性流程内化给 AI**”的判断，这个插件不应该是一个“让用户画流程图然后由 AI 照着走”的工具。它更准确的定位是：**一个用户可编辑的约束结构层，架在 DSH 的 subagent 执行能力之上，把“什么必须由人决定、什么可以委派、什么算通过”从对话中抽出来，变成可版本化、可审计、可中断恢复的工程对象。** 如果做成“用户画 DAG、AI 填节点”的形态，它会退化成又一个固定流水线编辑器；DSH 的 subagent 已经能做到按任务形状即时拆分和执行，再给用户一套更细的步骤规定，边际价值很低。真正缺的是**约束的可编程性**——让用户定义节点之间的契约、门禁和仲裁规则，而不是定义每一步的 prompt。

### 流程定义：用户编排的是约束，不是执行脚本

DSH 的 workflow seam 允许运行“模型编写的编排脚本”来启动 subagent，但脚本的编写者是模型，不是用户，且脚本执行在 `node:vm` 中，已知存在通过 `agent.constructor('return process')()` 逃逸到宿主进程的路径。因此，插件不应把用户定义的流程直接编译成 workflow seam 的脚本交给引擎执行——那等于把用户编排权转交给了模型或一段有逃逸风险的 VM 代码。

插件应当维护**自己的流程定义层**，用户编排的产物是一份结构化的流程规格，其中每个节点声明的是：**这个节点由哪个 agentPreset 执行、接收什么类型的输入、必须产出什么形状的输出、以及它的产出在什么条件下才能被下游消费**。DSH v0.2.1-alpha.3 已经支持在 spawn 子 Agent 时指定独立的 `agentPreset` 和 `toolFilter`，这为“节点=角色能力边界”提供了原生基础。用户编排的不是“先做 A 再做 B”，而是“A 的产出必须满足 schema S 且通过验证器 V，B 才能启动，B 无权访问 C 的工具”。

流程定义本身应当以**不可变版本**的形式保存。DSH 社区中已有实践将节点声明为 `type@version`，发布后的流程固定到不可变 revision。这不是工程上的洁癖，而是问责结构的前提：当一次运行出了问题，你必须能精确回答“当时执行的是哪一版约束规则”。

### 节点类型：用少量原语覆盖验证与问责

节点类型应当保持克制，优先支持那些**无法被简单委派给单个 subagent 一次性完成**的语义。至少需要以下几类：

**执行节点**是最基本的形态，绑定一个 `agentPreset`，在独立会话中运行，只向上游返回声明过的产物，中间步骤不进入编排层的上下文。这与 DSH subagent 的 spawn 语义一致：子 Agent 在自己的会话里完成工作，父级只拿到结果。

**门禁节点**是插件存在的核心理由。它不执行生成任务，而是暂停流程，把上游节点的产物、当前运行上下文和待决选项暴露给人，等待批准、拒绝或修改后恢复。DSH 生态中已有 `dsh-gatedflow` 将 gate 作为控制流的一等节点，通过对话面板卡片完成审批。插件应当把门禁设计成**可以出现在任意两条边之间**，而不是只能作为流程终点。门禁的判定依据可以是上游产物的 schema 校验结果、一个独立 Judge agent 的核验意见，或者纯粹的“此处必须由人签字”。

**仲裁节点**用于处理多个并行执行节点产出的冲突。它启动一个独立的 Judge subagent，该 Judge 与执行者使用不同的 agentPreset，只能看到冲突的产物和用户的原始意图声明，输出裁决和理由。这对应的是“验证不能由生成者自己完成”的原则。

**汇合节点**负责把多个上游节点的产物按契约合并为下游可消费的输入，并在合并时执行类型和完整性检查。

这些节点原语足以覆盖大多数复杂工程工作流中的问责需求，而不需要把流程语言膨胀成通用编程语言。

### 数据契约与边语义：流程的实质在边上，不在节点里

节点之间的边不应是简单的“上一步完成后触发下一步”。每条边至少承载三层语义：**产物传递的 schema 约束**（下游节点接收到的输入必须满足什么形状）、**触发条件**（上游产物在什么判定结果下才允许进入下游，比如门禁通过、仲裁裁定“接受”、校验器返回 pass）、以及**失败语义**（上游失败时，下游是阻塞、跳过、还是进入降级分支）。DSH 的 workflow seam 中 `meta` 和 `args` 是普通 JSON 数据，引擎会在运行前用 schema 校验，这提示了“契约先于执行”的模式。插件应当把同样的原则前移到流程定义层：**在流程启动之前，就校验节点之间的契约是否自洽**，而不是等运行时才发现某个节点的输出根本没有下游能消费。

### 执行引擎与状态：插件自身持有编排权，不外包给模型或 VM

插件不应把编排决策交给一个“编排 Agent”逐轮决定。DSH 的 subagent 机制已经能做到模型按任务形状自主拆分，但如果插件要提供用户可编排的约束结构，编排的执行权就应当留在插件自己的状态机里。具体来说，插件注册一个 `service`（而非仅一个 tool），持有流程运行的状态机：当前活跃节点集合、已完成节点的产物快照、待决门禁列表、每条边的触发条件求值结果。

每次节点执行仍然通过 DSH 的 subagent seam 启动子 Agent，但**启动哪个 agentPreset、传递什么输入、如何解读输出、是否放行到下游**，由插件的编排器决定，而不是由子 Agent 自己判断“我完成了”。这直接回应了上一轮讨论中的观察：让智能体自己审查自己的完成状态，准确率接近抛硬币。DSH 的 session 日志本身就是持久化的，且存在 `session-checkpoint-policy` 这类在特定检查点批量写入的机制，插件应当把流程运行状态写入 session 可恢复的持久化层，而不是只在内存中维护。当一次运行在门禁处暂停数小时甚至数天后恢复，状态机必须能从持久化快照中精确重建，包括每个已完成节点的产物和每条边的判定记录。

### 安全边界：用户编排的流程不能获得超越其工具授权的执行力

用户定义的流程如果可以被用来动态指定 `toolFilter` 或绕过 `agentPreset` 的工具清单，就会成为一个权限提升通道。DSH 的 permission-preset 将 sandbox mode 和 approval policy 捆绑为命名预设，这是可以借用的模式：**流程定义中引用的 agentPreset 和工具集，必须是用户在 DSH 中已经有权使用的子集**，插件在流程发布时做一次静态校验，在每次节点启动时再做一次运行时校验。流程本身不能声明它“需要”某个用户没有的工具；它只能声明它“使用”某个已存在的预设。此外，门禁节点审批的产物快照应当与触发门禁时的流程版本绑定，防止在暂停期间流程定义被静默修改后恢复执行。

### 与 DSH 原生能力的关系：编排层而不是替代层

这个插件与 DSH 已有能力的关系需要划清，否则会变成重复造轮子。**subagent 负责“执行一个被定义清楚的任务”**，插件负责“定义什么任务在什么约束下可以被执行、执行结果如何被验证、以及何时必须停下来”。**workflow seam 负责“在单次运行中并行启动多个子 Agent 并收束结果”**，插件不与之竞争，而是在需要批量并行执行一组同构节点时，将这一组节点的调度委托给 workflow seam 或直接通过 subagent 并发启动，但收束后的结果仍然要经过插件的边条件判定才能进入下游。**session/checkpoint 负责“持久化原始事件流”**，插件在其上维护流程运行的结构化状态，二者不是替代关系，而是不同粒度的记录：session 日志回答“发生了什么”，流程状态回答“现在处在约束结构的哪个位置、下一步被什么条件允许”。

这个设计的最终检验标准不是“AI 能不能在插件里全自动跑完一个流程”，而是：**当一个节点的产物有问题时，插件能不能精确指出是哪条契约没有被满足、哪个门禁本应拦截但没有被定义、以及这次运行使用的是哪一版流程约束。** 如果做到这一点，它就不是在给 AI 加流程负担，而是在为上一轮讨论中“流程从操作性规定转向约束性框架”提供一个可操作、可版本化、可问责的工程实现。

用户：
游戏开发流程中，部分环节的工作ai无法完成，需要人来产出。所以流程中部分环节由ai向人提出需求，由人完成并交付给ai。考虑这一点，插件的设计方案和理念应该是怎样的？

AI：
把“人向 AI 交付”纳入工作流，关键不在于增加一种“等待人工”的节点类型，而在于**重新定义人在流程中的本体论位置**。上一轮的设计把人放在“门禁”里——流程暂停，等人签字，然后恢复。但“AI 向人提出需求、人产出交付物”不是门禁，它是**生产环节**。门禁的语义是“允许/拒绝”，而人在这里的语义是“提供 AI 无法自行生成的东西”。如果只用门禁原语来承载这种交互，流程会把人的产出当作一个布尔值来处理，而不是当作一个有形状、有质量、需要被下游消费的工程对象。插件需要为“人作为能力提供者”建立一等公民的节点类型和契约体系。

### 理念：人不是流程的阻塞点，而是一个有交付契约的能力节点

现有生态中已经出现了把人类操作建模为结构化接口的尝试。DSH 社区的 `dsh-human-task` 插件让 Agent 暂停，等待用户完成 GUI 操作、游戏测试或视觉验证等现实任务，并以结构化 JSON 返回结果。Human Tool 框架则更进一步，把人的能力、信息和权威暴露为可调用的工具 schema，使 Agent 能根据相对优势动态调用人类输入。这些实践的共同方向是：**人不再是一个需要被“等待”的外部条件，而是一个可以被“请求”和“验收”的端点。**

但仅有“可调用”还不够。游戏开发中的人向 AI 交付，与客服场景中的人接管对话有一个根本区别：**客服交接的产物是“对话的继续”，而游戏开发交接的产物是“下一道工序的输入”。** 一个概念设计稿、一段手动调校的动画曲线、一个“这个 Boss 打起来够不够紧张”的主观判断——这些东西如果没有被包装成下游节点能够消费的形状，AI 拿到手也不知道该拿它做什么。因此，插件的核心设计对象不是“如何通知人”，而是**“如何定义人对 AI 的交付契约”**。

### 请求节点：结构化的需求，而不是一条消息

AI 向人提出的需求，至少需要携带四层信息才能被可靠地执行和验收。A2H 协议将 Agent 到人的交互拆为 INFORM、COLLECT、AUTHORIZE、ESCALATE、RESULT 五种意图，其中 COLLECT（索取结构化数据）和 AUTHORIZE（带认证的授权）直接对应“人需要提供 AI 无法自行产生的东西”。AGTP 的 ESCALATE 语义则要求携带结构化的 reason（如 confidence_threshold、scope_limit、ambiguous_instruction）、完整上下文、优先级和截止时间。插件可以借鉴这种分层，但需要针对游戏开发的生产性交接做扩展。

请求节点应当声明：

**交付物的类型与验收契约。** 人需要交付的不是“一个文件”，而是一个满足特定形状的对象。概念设计稿可能需要附带风格约束的标注；手动调校的动画曲线可能需要满足特定的时长和关键帧密度；一个“战斗手感是否到位”的判定可能需要以结构化量表而非自由文本返回。Agent 交付验收标准（ADAS）中有一条原则值得直接借用：**“完成”意味着被写下来，而不是被说出来**——人类交付物必须落为一个可被下游解析和校验的 artifact，而不是聊天里的一句“我做好了”。

**请求的触发理由与不可替代性声明。** 请求节点必须携带“为什么这个环节必须由人完成”的结构化理由。这不仅是给用户看的说明，更是流程可审计性的基础：当一次运行完成后，你需要能回答“哪些环节的产出是人类提供的、依据是什么”。游戏开发的任务分类框架提供了一个有用的坐标：规格清晰度高、迭代敏感性低的任务适合 AI；规格模糊且需要多轮试错的任务适合人。请求节点应当把这一判断显式化，而不是隐式地假设“AI 做不了就转给人”。

**等待语义与恢复路径。** 人不是即时响应的组件。请求节点必须定义等待期间流程实例的状态：哪些下游节点被阻塞，哪些并行的无关分支可以继续，请求过期后是重新请求、降级到 AI 的次优产出、还是终止该分支。Microsoft Agent Framework 的 HITL 原语提供了关键参照：当执行器发出请求时，工作流分支被**持久挂起**，状态存活于存储中，重启或瞬时故障不会丢失等待中的请求；响应携带 request id 和工作流实例 id，被自动路由回精确的等待执行器。插件必须把这一语义纳入自身的流程状态机：**请求节点的“等待”是一个可持久化的状态，而不是内存中的一个 Promise。**

### 交付物的验收：人交来的东西，AI 不能无条件接受

这是整个设计中最容易被低估的环节。当 AI 向人提出请求时，一个自然的错误是：人交什么，AI 就当作什么用。但在复杂工程工作流中，**人的产出同样需要经过契约校验**，理由与人审查 AI 产出的理由完全相同——未经校验的输入会成为下游错误的根源。

DSH 生态中的 `dsh-preset-requirement-confirm` 展示了“先确认、后执行”的模式：模型先把需求拆成子需求，用结构化问卷逐题确认，用户提交之后模型才开始执行。这个模式可以反向借鉴到交付侧：人提交的产物同样应当经过一个**交付验收节点**，该节点检查产物是否满足请求节点声明的契约，如果不满足，要么退回给人重新交付，要么降级到备选路径，要么由仲裁节点决定是否接受一个部分满足的版本。

门禁设计中的“验收与人工审批”层提供了一个结构化的参照：输入与权限、任务拆分、候选结果、验收与人工审批、下游使用——**未经批准的候选结果不应被视为正式交付物**。在人向 AI 交付的场景中，这个“验收层”的主体发生了倒转：不是人验收 AI，而是 AI（或一个独立的验证 subagent）验收人的产出是否符合下游消费的条件。这听起来可能反直觉，但它是工作流一致性的必然要求：**如果 AI 的产出需要被验证才能进入下游，人的产出没有理由例外。**

### 人不能成为权限提升通道

请求节点在设计中引入了一个新的攻击面：如果 AI 可以发起请求，而人的交付物被流程无条件接受，那么一个被操纵或出错的 AI 可以通过“请求人提供某个东西”来诱导人绕过原本的工具权限或审批门禁。AGTP 在 DELEGATE 中有一条关键安全约束：**授权范围必须是委派方自身授权范围的严格子集**，服务器必须强制这一点，这是协议层面对“权限洗白”的防御。

请求节点应当继承同样的原则：**人通过请求节点提供的权限或能力，不能超出该节点在流程定义中已经声明的范围。** 一个美术评审节点请求人提供“视觉参考”，不能因此让人获得向生产环境写入资产的权限；一个叙事节点请求人“确认角色动机”，不能因此让人的确认被当作跳过后续内容审核的通行证。人的交付物是**数据**，不是**执行权**。如果某个环节确实需要人执行一个 AI 无权执行的操作，那应当被建模为一个显式的“人工执行节点”，其权限边界由流程定义预先声明并经过校验，而不是由请求节点的运行时行为动态授予。

### 与 DSH subagent 体系的关系：请求节点是编排层的消费者，不是 subagent 的替代

DSH 的 subagent 机制处理的是“把一个定义清楚的任务委派给一个独立会话执行”。请求节点处理的是“一个子 Agent 在执行中遇到一个它不应或不能自行解决的缺口，需要向上游编排层发起一个对人请求”。两者的关系应当是：**子 Agent 不直接阻塞等待人。** 子 Agent 在自己的会话中检测到缺口，向编排层返回一个结构化的“缺口声明”，然后结束本次执行；编排层根据缺口声明创建或激活一个请求节点，挂起下游依赖，等待人交付；人交付并通过验收后，编排层再启动一个新的子 Agent 会话（或恢复原有上下文）来消费该交付物并继续。

这避免了让子 Agent 长时间空转等待，也把“什么需要人、人需要交什么、交了之后怎么用”的决策权留在编排层，而不是散落在各个子 Agent 的运行时状态里。`dsh-preset-route` 的实践提供了一个有用的模式：它不执行任务，只做路由和写自包含的任务简报，按目标 preset 的真实输入契约来写。请求节点可以借鉴同样的思路：**为“人”这个特殊的执行者写一份自包含的、按交付契约组织的请求简报**，而不是把 AI 内部的上下文碎片直接倾倒给人。

### 设计边界：不要把人变成流程的瓶颈

最后需要明确这个插件**不应该**做什么。它不应该把人向 AI 的交付设计成一个必须即时响应的同步调用。游戏开发中的人向交付往往是非连续的、异步的、需要离线思考的。请求节点需要支持“提交后离开，稍后回来查看”的节奏，流程状态必须能在无人值守时持久存活。

它也不应该试图把所有人类判断都形式化为请求节点。上一轮讨论中已经确认，游戏开发中最不可替代的人的判断——一个机制是否有趣、一个场景是否传递了想要的张力——无法被完全预先规格化。请求节点适合承载的是**那些有明确交付形状、只是 AI 在当前能力下无法可靠生成的东西**：手动精修的美术资产、需要真实世界经验验证的手感判断、涉及法律或 IP 边界的授权决策。对于那些连“需要什么”都还说不清楚的判断，它应当被保留在流程的**设计时**由人完成，而不是被硬塞进运行时的一个请求节点里。

这个设计的检验标准是：**当一次运行在人向交付处暂停又恢复后，流程能够精确说出人交付了什么、该交付物在什么条件下被接受、以及它被下游的哪个节点以什么方式消费。** 如果做到这一点，人向 AI 的交接就不再是工作流中的一个“洞”，而是一个有契约、有验收、有问责的工程环节。
